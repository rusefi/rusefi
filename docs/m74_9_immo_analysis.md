# m74_9 immobilizer analysis notes

Этот документ содержит всё, что известно об иммобилайзере m74_9 / Itelma I865LB52 (Lada/Largus),
чтобы последующие сессии могли продолжать работу без повторной разведки.

---

## Текущий статус (обновлено 2026-08-14)

### Что исправлено

**Устранена мёртвая блокировка** в `firmware/config/boards/m74_9/m74_9_can.cpp`:

- Старый код запускал триггер при `byte4 == 0x44` (поворот ключа на старт).
- BCM **никогда** не выставляет `byte4=0x44`, пока IMMO-хэндшейк не завершён.
- rusEFI никогда не посылал триггер → BCM никогда не посылал вызов 0x0714 → стартер не крутил.

Исправление:
- Триггер теперь запускается при `byte4 != 0x00` (первый кадр BCM после включения зажигания).
- Задержка триггера: 100 мс → 1000 мс (оригинальный ЭБУ посылает ~1.5 с по трейсам).
- `m74_9_isImmobilizerBlocking()` теперь учитывает `m74_9ImmoEnabled` и `m74_9ImmoOff`:
  возвращает `true` только если IMMO включён в конфиге, физический обход не активен
  и аутентификация ещё не пройдена. Когда IMMO выключен — движок заводится без обмена.

### Обнаружено (SWD/JTAG сессия 2026-08-14)

- **Триггер 0x0713 — случайные 8 байт** каждый запуск (вероятно AT32F435 TRNG).
  BCM вычисляет Frame1+Frame2 из этого триггера по неизвестному алгоритму.
  rusEFI шлёт фиксированный счётчик — BCM отвечает другим форматом.

- **Окно приёма 0x0714 — 1.2..10.3 мс** после 0x0713 (avg 7 мс по 5 парам).
  Ручная отправка через PCAN-View (~100 мс) всегда опаздывает.

- **Формат Frame1**: байт[0] ДОЛЖЕН иметь бит 0x40 (RESPONSE-формат).
  Во всех 5 парах оригинального ЭБУ Frame1[0] ∈ {0x66, 0xCF, 0x4A}.
  Данные `26 17 14 F0...` (от BCM→rusEFI) не принимаются оригинальным ЭБУ.

- **ЭБУ не проверяет challenge против своего trigger** — FUN_08201E2C проверяет
  только key_type==1 и session_word==0xFF00/0xFF01. Любой корректно-форматный
  0x0714 (с правильным байт[0]) должен приниматься.

- **Корректные тестовые данные** (из orig_1.trc, пара 1):
  - Frame1: `66 0B E1 E2 A3 4B 81 40`
  - Frame2: `B4 56 33 A0 49 9A 01 EC`

### Что ещё не сделано

`computeImmoResponse()` и `computeImmoQuickResponse()` — заглушки, возвращающие `false`.
Алгоритм ответа не реализован. Движок запустится (IMMO не блокирует), но BCM будет
периодически посылать повторные вызовы 0x0714, на которые ECU не отвечает.

Breakpoint на `0x082078D4` (BLX R3 = вход в SLib) ещё не сработал:
нужны правильные данные (Frame1[0] с битом 0x40) + автоматическая отправка < 10 мс.
См. `immo_respond.py` и инструкцию ниже.

## Разница между IMMO ON / IMMO OFF бинарниками

Файлы лежат в корне репозитория:
- `LARGUS_TUN_V14-8_ANTIJRK_OFF_UOZNEW_OTSKOK-6_AFR09_IMMOON.bin`
- `LARGUS_TUN_V14-8_ANTIJRK_OFF_UOZNEW_OTSKOK-6_AFR09_IMMOOFF.bin`

Оба файла — полные 1 МБ образы flash (`0x08000000…0x080FFFFF`). Сравнение `cmp -l`:

| Byte (1-based) | Hex offset | IMMO ON | IMMO OFF | Примечание |
|---|---|---|---|---|
| 478202 | `0x74BF9` | `0x01` | `0x00` | **Флаг включения иммобилайзера** |
| 524285 | `0x7FFFC` | `0xA2` | `0xDE` | часть 4-байтовой |
| 524286 | `0x7FFFD` | `0xB2` | `0x1D` | контрольной |
| 524287 | `0x7FFFE` | `0x4C` | `0xBE` | суммы/подписи |
| 524288 | `0x7FFFF` | `0xC6` | `0xF0` | (изменилась из-за байта выше) |

Окружение байта-флага:

```
0x08074BF0: 80 3e 00 4b  ff ff 00 00  01 [01/00] 01 00  00 00 00 00
```

Байт `0x08074BF9` входит в калибровочную таблицу дескрипторов по адресу `0x0804A900` (таблица найдена в `Read_FULLFLASH_I865LB52_w2404b1____(240626_103727).bin`). В оригинальном полном дампе этот же байт равен `0x01` (IMMO включён). 4 байта по `0x0807FFFC` — это, вероятно, checksum/signature первого 512 КБ банка, которая пересчитывается при изменении любого байта калибровки.

**Практический вывод**: для программного отключения иммобилайзера в оригинальной прошивке достаточно сбросить бит `0x08074BF9` → `0x00` и пересчитать контрольную сумму банка. В rusEFI аналогичный конфигурационный бит — `m74_9ImmoEnabled`, но он действует на уровне firmware, а не перезаписывает байт в оригинальной калибровке.

## Протокол CAN (подтверждён анализом трейсов PCAN-View)

### Идентификаторы сообщений

| ID     | Направление | Период | Описание |
|--------|-------------|--------|----------|
| 0x0350 | BCM → ECU   | 100 мс | Статус BCM; byte4 кодирует фазу IGN/пуск/реле/работа |
| 0x0303 | BCM → ECU   | 100 мс | Статус реле; bit1 byte5 = реле стартера активно |
| 0x0714 | BCM → ECU   | ~200 мс (пересылка) | IMMO-вызов от BCM |
| 0x0713 | ECU → BCM   | по событию | IMMO-триггер (инициирует) + ответ (после вызова) |
| 0x01F6 | ECU → BCM   | 10 мс  | Статус двигателя |
| 0x0189 | ECU → BCM   | 10 мс  | RPM primary (0x3200 в покое!) |
| 0x0186 | ECU → BCM   | 10 мс  | RPM aux |
| 0x018A | ECU → BCM   | 10 мс  | RPM aux2 |
| 0x0217 | ECU → BCM   | 10 мс  | Статус ECU |
| 0x02A9 | ECU → BCM   | 10 мс  | Heartbeat |
| 0x02C6 | ECU → BCM   | 20 мс  | Статика |
| 0x05E2 | ECU → BCM   | 1000 мс| Keepalive |
| Burst  | ECU → BCM   | 100 мс | 11 кадров идентификации (05DA, 036E, 03A5, …) |

### Полный цикл аутентификации

1. ECU включает зажигание → ждёт ~1.5 с
2. ECU посылает 0x0713 **триггер** T (8 байт, криптографически значимые — см. ниже)
3. BCM проверяет T, отвечает двумя 0x0714 кадрами подряд (~0.2 мс между ними) = 16-байтный вызов
4. ECU вычисляет ответ (~15–20 мс) и посылает 0x0713 **ответ** R (8 байт)
5. BCM проверяет ответ → если верен, разрешает старт
6. BCM начинает периодически посылать 0x0714 quick-check (1 кадр, 8 байт) каждые ~200 мс
7. ECU отвечает на каждый quick-check в течение ~5 мс

**Ключевой факт**: 0x0713 — ЕДИНСТВЕННЫЙ CAN ID для трёх разных типов данных:

| Порядок | Данные в 0x0713 | Роль |
|---------|----------------|------|
| Первый | T (8 байт) | **Триггер** — инициирует IMMO, передаётся BCM |
| Второй | R (8 байт) | **Полный ответ** — после получения 2× 0x0714 |
| Третий+ | QR (8 байт) | **Быстрый ответ** — на каждый quick-check 0x0714 |

Пример из orig_1.trc:
```
905.6ms   0x0713: 52 83 db a6 47 69 c0 0d  <- триггер T
910.7ms   0x0714: 66 0b e1 e2 a3 4b 81 40  <- Frame1 от BCM
910.9ms   0x0714: b4 56 33 a0 49 9a 01 ec  <- Frame2 от BCM
926.3ms   0x0713: 9c b7 f8 ca 31 43 1b b6  <- полный ответ R
1110.6ms  0x0714: 0e ab fe 9d 35 1a f8 37  <- quick-check
1115.5ms  0x0713: b1 51 56 d1 46 83 cd 15  <- быстрый ответ QR
```

### Статусная машина BCM (0x0350, byte4)

| byte4  | Значение |
|--------|----------|
| `0x00` | BCM выключен / зажигание выключено |
| `0x04` | Зажигание включено, IMMO не пройден (CF состояние) |
| `0x44` | Ключ повёрнут на старт (crank switch) — только после IMMO! |
| `0x84` | Реле стартера активно (BCM выдал GND на реле) |
| `0xC4` | Двигатель работает |

**Важно**: BCM никогда не выставит `0x44` или выше, пока IMMO-аутентификация не пройдена.
Стартером управляет полностью BCM — пин starter relay на ECU не используется.

**Поле CF** в `0x0350 byte0`: если ECU посылает `0x0000` в первых двух байтах `0x0189`
(RPM baseline), BCM входит в режим CF-ошибки и отказывается закрывать реле стартера даже
при правильном IMMO. Обязательно посылать `0x3200` как baseline когда двигатель стоит.

## Гипотеза о криптографии триггера (высокая уверенность)

### Триггер 0x0713 — не простой nonce

Триггеры оригинального ЭБУ (по трейсам):
```
stol.trc:         60 fe a2 66 34 30 7f 6c
orig_1.trc:       52 83 db a6 47 69 c0 0d
orig_2.trc:       a5 ea 8a 93 26 55 30 dd
orig_3.trc:       45 d4 a5 c0 f6 a1 ea 72
ignon.trc:        08 41 99 4c 0b 81 a1 4c
ignon_and_start:  d0 81 cc 98 27 08 d8 06
rusEFI (fixed):   00 00 00 00 00 00 c0 00  <- фиксированный счётчик
```

### Доказательство: BCM проверяет триггер

BCM отвечает на 0x0713 двумя видами Frame1 (различающийся по биту 0x40 в байт[0]):

| Триггер источник | Frame1[0] | Бит 0x40 | Название |
|-----------------|-----------|---------|--------|
| Оригинальный ЭБУ (6 сессий) | 0x66, 0xCF, 0xCD, 0x4A | **ВСЕГДА SET** | RESPONSE-формат |
| rusEFI фиксированный | 0x26 | **НЕТ** | REQUEST-формат |

Вероятность случайного совпадения для 6 из 6 триггеров = (1/2)^6 = ~1.5%. **Не случайность.**

BCM отвечает RESPONSE-форматом (0x40 бит) только когда **верифицирует подпись**
триггера по общему ключу.

### Архитектура протокола

```
         SLib (адреса 0x08100000-0x081FFFFF, защищёно)
              │
         Ключ K (недоступен извне)
         ┌────┼─────────┐
         │        │        │
    [1] Генерация   [2] Проверка   [3] Вычисление
       T = SLib(K, N)    F1+F2 ?= ...   R = SLib(K, F1+F2)
         │                               │
         ↓ 0x0713                        ↓ 0x0713
         ↓                               ↓
  BCM: verify(K, T) -> OK -> compute F1+F2 = SLib_BCM(K, T)
                             ↓ 0x0714 F1+F2
```

- **[1] Генерация триггера**: `T = SLib(K, TRNG_nonce)` — подписанный nonce.
  rusEFI шлёт неподписанный счётчик → BCM видит невалидный токен → REQUEST-формат (0x26).
- **[2] Проверка Frame1+Frame2**: возможно `FUN_0820630C` (проверка flash-аттестации)
  (см. шаги 3-6 ниже). Может быть и SLib-верификация.
- **[3] Вычисление ответа**: `R = SLib(K, F1||F2)` — BLX R3 на `0x082078D4`.

Весь IMMO держится на **одном ключе K** в SLib. После прошивки rusEFI сохраняя SLib,
тот же защищённый K доступен через вызов SLib-функций.

### Практические следствия

1. rusEFI должен вызывать SLib для **генерации триггера** 0x0713, а не посылать фиксированный счётчик.
2. Также SLib нужен для вычисления ответа.
3. Вход в SLib — адрес в R3 на `0x082078D4`, считанный через LDR из таблицы.
4. **Оискать код генерации триггера** в flash (см. раздел ниже).

### Вызовы от BCM для rusEFI (новые данные 2026-08-13)

**Критическое наблюдение**: Frame1 = `26 17 14 F0 94 E7 29 7F` одинакова
для ВСЕХ 10 сессий rusEFI (только Frame2 случайна).

Это означает: Frame1 — фиксированный идентификатор BCM (не производная от триггера),
а Frame2 — случайный nonce.

Frame1 для rusEFI всегда: `26 17 14 F0 94 E7 29 7F`
```

  frame2=c0a376b3e9fdb85f  -> response НЕИЗВЕСТЕН
  frame2=e1f1651d533d54b8  -> response НЕИЗВЕСТЕН
  frame2=a2699d694b45d96e  -> response НЕИЗВЕСТЕН
  frame2=976ad10d9a3de065  -> response НЕИЗВЕСТЕН
  frame2=619adfc29b480a80  -> response НЕИЗВЕСТЕН
  frame2=f38352b522a50ddb  -> response НЕИЗВЕСТЕН
  frame2=8ddf022d20c69e89  -> response НЕИЗВЕСТЕН
  frame2=59ef563691af1d46  -> response НЕИЗВЕСТЕН
  frame2=ee8cc257e2644898  -> response НЕИЗВЕСТЕН
```

Чтобы получить ответы: поставить оригинальный ЭБУ, снять PCAN-дамп.
BCM пошлёт те же вызовы (Frame1=2617...), оригинальный ЭБУ даст ответы.

### Frame1 структурный анализ

Frame1 = `26 17 14 F0 94 E7 29 7F`
- Byte[0] = 0x26 = 38 (возможно, Service ID)
- Byte[1] = 0x17 = 23 (возможно, Sub-function ID)
- Byte[2] = **0x14** → n1=4, n2=1 — единственный байт с обоими nibble ≤ 4!
- Byte[3..6] = F0 94 E7 29 → r8 = 0xF094E729 (BCM's ключевой материал)
- Byte[7] = 0x7F → r5 = 0x7F (дополнительный параметр)

Паттерн `2617` найден в flash calibration по адресам:
- 0x0804E87A, 0x08063891, 0x08063A91
(вероятно, ожидаемый Frame1 хранится в калибровке ECU для проверки)

### Quick 8-байтный вызов → 8-байтный ответ (периодическая проверка)

```
challenge 0eabfe9d351af837 -> response b15156d14683cd15
challenge 4a90250e855128bf -> response 14a267bec8d8c3dc
challenge 63b95b1a3fbf41fe -> response 2fa71d4722835ea2
challenge 596e3885f2460f4a -> response 2cdf61de56551b86
challenge a00059b79f90a8ae -> response a225de4e470324b6
```

Что **проверено и исключено** при поиске алгоритма:
- XOR (все смещения), ADD, SUB mod 256 — нет константного ключа
- AES-128-ECB (все 16-байтные блоки flash в диапазоне 0x080400–0x090000) — не найдено
- SHA-1, SHA-256, MD5 — нет
- CRC32 — нет
- XTEA/TEA (32 раунда, LE и BE) — нет
- Простое чтение flash (ответы не найдены в бинарнике verbatim) — нет

Алгоритм **проприетарный**, использует ADD/XOR/shift с ключом из калибровочной области flash.

## Цепочка обработки CAN-приёма

```
CAN1_RX0_IRQ (0x08207432)
  → FUN_08207432  (выравнивание стека)
  → FUN_08206FB8(channel=0)  (универсальный CAN-диспетчер)
      читает CAN_RDT0R[15:8] = FMI (Filter Match Index)
      ищет обработчик в таблице 0x08209834
      → per-frame handler (для 0x0714 — хранит байты в SRAM 0x20000C14)
      → глобальный коллбэк *SRAM[0x20001BFC]
          → FUN_08204AB8 → таблица 0x082090E0 → обработчики по CAN ID
```

CAN1_RX использует **FMI** (индекс совпавшего фильтра), а не прямой CAN ID для диспатча.

## SRAM-таблица зарегистрированных функций

База: `0x20001018`, шаг: `0x54` на запись (индекс 0..6).
Каждая запись — структура с указателями на функции по разным смещениям.

**Зарегистрированные слоты (индекс 1, все адреса Thumb = нечётные)**:

| Смещение | Зарегистрированный адрес | Назначение |
|----------|--------------------------|-----------|
| `+0x04`  | `0x08202019` (fn @ 0x08202018) | Управление CAN-каналом |
| `+0x10`  | `0x08201AE1` (fn @ 0x08201AE0) | UDS DID обработчик (F188–F199) |
| `+0x14`  | `0x082017F9` (fn @ 0x082017F8) | Дополнительный обработчик |
| **`+0x34`** | **`0x08201E2D` (fn @ 0x08201E2C)** | **IMMO-обработчик вызова** |
| `+0x3C`  | `0x08201DF1` (fn @ 0x08201DF0) | Хранит flash_start, flash_size |
| `+0x40`  | `0x08201D85` (fn @ 0x08201D84) | Вызывает вычислительную функцию |
| `+0x44`  | `0` | Парный параметр к +0x40 |
| `+0x4C`  | `0x082017D9` (fn @ 0x082017D8) | Дополнительный обработчик |

Регистраторы (устанавливают слоты в таблице):
- `0x08203718` → записывает в `+0x34` (IMMO-обработчик)
- `0x08203734` → записывает в `+0x3C`
- `0x08203750` → записывает в `+0x40` и `+0x44`
- `0x08203770` → записывает в `+0x4C`
- `0x082036C4` → записывает в `+0x04`
- `0x082036E0` → записывает в `+0x10`
- `0x082036FC` → записывает в `+0x14`

Инициализация: `FUN_08202038` (PUSH @ 0x08202038) вызывает все регистраторы при старте.

## Цепочка вычисления IMMO-ответа

### Шаг 1 — Вычислитель 0x082027A4

Вызывается, когда нужно вычислить ответ на 16-байтный вызов BCM:

```
FUN_082027A4(r0=session_handle)
  r3 = SRAM[0x20000C14] count word  (> 3)
  r4 = SRAM[0x20000C15] & 0x7F      (key_type = 1)
  r1 = SRAM[0x20000C15]             (table_index)
  r2 = 0x20001018 + r1 * 0x54       (table entry ptr)
  r6 = [r2, #0x34]                  (fn ptr → FUN_08201E2C)
  blx r6  ← вызов IMMO-обработчика с:
    r0 = key_type (1)
    r1 = session_word (bytes [2:3] из 0x20000C14)
    r2 = 0x20000C18  (data_ptr + 4, начало данных вызова)
    r3 = count - 4
    sp+0 = 0x20000C1C  (буфер ответа)
    sp+4 = 0x3FC
    sp+8 = &output_len  (счётчик выходных байт)
```

### Шаг 2 — IMMO-обработчик FUN_08201E2C (@ +0x34)

```c
FUN_08201E2C(r0=key_type, r1=session_word, r2=data_ptr+4, r3=count-4):
    // Проверки:
    FUN_082037D8() → возвращает SRAM[0x200003FE] (должен быть 1)
    assert key_type == 1
    assert session_word == 0xFF00 или 0xFF01

    // Парсинг данных вызова (первый байт кодирует длины):
    byte0 = data[0]
    n1 = byte0 & 0xF   (кол-во байт для r8, должно быть ≤ 4)
    n2 = byte0 >> 4    (кол-во байт для r5, должно быть ≤ 4)
    r8 = big-endian аккумулятор из data[1..n1]       (flash_start?)
    r5 = big-endian аккумулятор из data[n1+1..n1+n2] (flash_size?)

    // Проверка SRAM[0x200002C8]:
    if == 0: вызвать FUN_08204B54 (первичная инициализация)
    if == 1: вызвать FUN_0820630C(r8, r5) (собственно вычисление)

    // FUN_08201E2C ВСЕГДА возвращает не-0 (асинхронный режим).
    // Вызывающий код при не-0 идёт в "error path" → FUN_08202254,
    // которая управляет асинхронным состоянием.
```

### Шаг 3 — FUN_0820630C (асинхронный движок)

```c
FUN_0820630C(r0=flash_start, r1=flash_size):
    FUN_0820566C(flash_start + flash_size - 1)  // проверка диапазона
    SRAM[0x20001B16] = 1  // state = busy
    FUN_082057F4()   // сброс FLASH_CR прерываний
    FUN_0820587C()   // очистка FLASH_SR флагов
    FUN_08205910()   // включение EOPIE прерываний
    FUN_08205950(flash_start, flash_size)   // настройка сессии
    SRAM[0x20001B60..] = {flash_start, flash_size, ...}
    FUN_08205D24()   // запуск операции (SER/MER биты в FLASH_CR)
    FUN_08205AB0(1)  // проверка готовности канала
```

### Шаг 4 — Flash ISR FUN_082063FC

```
FLASH_IRQHandler (0x082063FC):
    читает FLASH_SR (0x40023C00 + 0x0C), проверяет EOP (бит 5)
    если EOP set → очищает флаг, вызывает *SRAM[0x20001B88]
    SRAM[0x20001B88] содержит коллбэк, зарегистрированный при настройке
```

### Шаг 5 — FUN_08206108 (вычисление на flash-данных)

```c
FUN_08206108(r0=flash_start, r1=challenge_data_ptr, r2=length):
    FUN_08205A3C(flash_start, challenge_data_ptr, length):
        SRAM[0x20001B60]   = flash_start
        SRAM[0x20001B60+4] = challenge_data_ptr
        SRAM[0x20001B60+8] = length
        lookup в таблице 0x082093D8 (flash region table)
        SRAM[0x20000100]   = hw_variant byte из таблицы
        FUN_082059DC()  // настройка flash hardware
        FUN_08205A2C()  // дополнительная настройка
    FUN_08205AB0(2)
    FUN_08208408(2)   // диспатч → асинхронный коллбэк
```

### Шаг 6 — FUN_082056D4 (базовая проверка flash)

```c
FUN_082056D4(r0=flash_addr, r1=flash_size) -> 0 или 1:
    for i in 0..flash_size-1:
        if flash[flash_addr + i] != 0xFF:
            return 0   // регион запрограммирован (не стёрт)
    return 1           // регион стёрт (все байты 0xFF)
```

Эта функция вызывается для каждого байта/чанка результата в состоянии state=3/5/6 в
`FUN_082061F0`. Результат (0 или 1) накапливается в буфере ответа. Это не прямое чтение
flash — это **flash attestation** (проверка что firmware запрограммирована).

### Шаг 7 — Коллбэк FUN_08201A48 (отправка ответа)

```c
FUN_08201A48(r0=status, r1=data_or_zero):
    if r0 == 1 and r1 == 0:
        // "ключ верифицирован" — посылает [1, 0xFF, 0, 0] с cmd=0x31
        FUN_0820378C(r0=0, r1=0x31, r2=stack_buf, r3=4, flag=1)
        // первый байт CAN = 0x31 | 0x40 = 0x71

    if r0 == 2 and r1 == 0:
        // "ответ вычислен" — посылает данные из SRAM[0x200002D0]
        ldr r2, SRAM[0x200002D0]   // указатель на данные ответа
        FUN_0820378C(r0=0, r1=0x36, r2=r2, r3=1, flag=1)
        // первый байт CAN = 0x36 | 0x40 = 0x76
        // SRAM[0x200002D2] = длина данных (16-битная)
        // SRAM[0x200002D4] = flash-курсор (сдвигается на length каждую итерацию)
        // SRAM[0x200002DC] = счётчик (сравнивается с flash_size для цикла)
```

**Примечание**: наблюдаемые ответы CAN начинаются с байт 0x9C, 0xBF и т.д.
Первый байт CAN **не** соответствует `cmd|0x40` через `FUN_0820378C`.
Возможно, окончательный ответ формируется иным путём или через другую точку отправки.

## Коррекция: BLX 0x082078D4 не вызывает SLib (открыто 2026-08-14)

### Новая картина

**BLX R3 на 0x082078D4 не является входом в SLib.**
Он вызывает функцию из внутренней таблицы обёрточного (wrapper) региона.

Таблица функций по адресу `0x08209A60` (загружается в R2 перед BLX):
```
[0] 0x08205F59   [1] 0x08205F89   [2] 0x08205F9D
[3] 0x0820600D   [4] 0x08206109   [5] 0x082061D5
[6] 0x082061E1   [7] 0x082062E9
```
Все адреса в wrapper-диапазоне (0x082xxxxx).
`FUN_08206109` = `FUN_08206108` из шага 5 цепочки (флаш-аттестация).

### Реальные вызовы SLib: 36 прямых BL/BLX в основном фермваре

Python-поиск по дампу нашёл 36 прямых `BL/BLX <target>` инструкций,
цель которых находится в SLib-диапазоне (0x081xxxxx).
Все 36 находятся в основном фермваре (0x080xxxxx), а НЕ в wrapper.

Горячие области:

| Область вызовов | Кол-во | Цели SLib |
|----------------|--------|----------|
| `0x08089xxx`   | 7      | 0x08109778, 0x081097F4, 0x081097FC, 0x08109C0C, 0x081098A4, 0x08109D8A, 0x08109DD2 |
| `0x0808Axxx`   | 4      | 0x0810AE20, 0x0810ADCE, 0x0810AE8E, 0x0810AE3C |
| `0x0808Cxxx`   | 4      | 0x0810D40C, 0x0810D0AC, 0x0810D0B4, 0x0810D0BC |
| `0x0806xxxx`   | 2      | **0x081F102A, 0x0819AFEE** |
| `0x080ACxxx`   | 3      | 0x081361D0, 0x081AD9B8, 0x081A2C3C |
| Прочие    | 16     | разрозные SLib-адреса |

**Наиболее вероятный генератор триггера в 0x08069xxx** (два SLib-вызова):
- `0x08069028` -> SLib `0x081F102A` 
- `0x080697D0` -> SLib `0x0819AFEE`

Горячая область 0x08089xxx-0x0808Cxxx (примерно 15 вызовов) — скорее всего
крипто-движок (AES/HMAC) или система аутентификации независимая от IMMO.

### Важное следствие

Алгоритм IMMO-ответа реализован в **читаемом wrapper** (0x082xxxxx) без прямых
вызовов SLib. Если алгоритм действительно flash-аттестация —
его можно реализовать в rusEFI **без знания алгоритма SLib** (rusEFI читает те же
адреса флаша что и оригинальный ЭБУ, если SLib сохранён).

Для **генерации триггера** SLib, вероятно, нужен вызов одной из функций
0x08069xxx (SLib 0x081F102A или 0x0819AFEE).

### Следующие шаги по SLib

1. **Breakpoint 0x08069028** и **0x080697D0** — поймать SLib-вызов во время генерации 0x0713.
2. **Breakpoint 0x08089000-область** — поймать SLib во время IMMO-обмена.
3. **Unicorn-эмуляция** 0x080696xx-0x080698xx с захватом вызовов SLib.

### Карта SLib-вызовов (`find_trigger_gen.py`)

```
Caller       -> SLib target
0x08069028   -> 0x081F102A  *вероятно генерация триггера*
0x080697D0   -> 0x0819AFEE  *вероятно генерация триггера*
0x08089xxx   -> 0x08109xxx  (хотспот 15 вызовов, вероятно AES-движок)
0x080AC188   -> 0x081361D0  другое
0x080B5F9C   -> 0x08142704  другое
...
```

### C. Конфигурационный бит

`bit m74_9ImmoEnabled` и `bit m74_9ImmoOff` определены в `firmware/integration/rusefi_config.txt`.
После повторной генерации (`touch firmware/integration/rusefi_config.txt`) появляются
в `engine_configuration_generated_structures_m74_9.h`.

## Формат буфера вызова в SRAM (гипотеза)

При приёме 0x0714 BCM посылает данные, которые CAN-обработчик складывает
в SRAM начиная с 0x20000C14:

```
[0x20000C14] byte  count     = полный размер буфера (ожидается > 3)
[0x20000C15] byte  key_type  = 0x01 (стандартный ключ)
[0x20000C16] byte  session_hi= 0xFF
[0x20000C17] byte  session_lo= 0x00 или 0x01  → session_word = 0xFF00/0xFF01
[0x20000C18] 8 байт frame1_data  (байты 0–7 первого 0x0714 кадра)
[0x20000C20] 8 байт frame2_data  (байты 0–7 второго 0x0714 кадра)
```

Первый байт данных `[0x20000C18]` кодирует: `low_nibble=n1` (≤4), `high_nibble=n2` (≤4).
Все наши наблюдаемые вызовы имеют первый байт с обоими nibble > 4 → либо байты
хранятся иначе, либо SRAM заполняется CAN-обработчиком с предобработкой.

## Живая трассировка IMMO-обмена

### Новое ключевое наблюдение: IMMO OFF = нет триггера

Снят новый CAN-дамп с калибровкой `IMMOOFF` (байт `0x08074BF9 = 0x00`). В этом режиме ЭБУ **вообще не посылает** кадр `0x0713`. BCM также не шлёт `0x0714`, и иммобилайзер не участвует в запуске.

Это подтверждает, что байт `0x08074BF9` — именно аппаратный флаг включения IMMO: когда он `0x00`, весь протокол challenge-response отключён на стороне ECU.

### Контрольные суммы во FULL_FLASH

Дамп `Read_FULLFLASH_I865LB52_w2404b1____(240626_103727).bin` содержит сохранённые КС:

| Название | Значение | Адрес в flash | Примечание |
|---|---|---|---|
| КС BOOT | `94B8B6D7` | `0x08022DFFC` | bootloader region checksum |
| КС калиб. | `DD5630D0` | `0x0807FFFC` | calibration region checksum |
| КС прог. | `61F8857E` | `0x080FFFFC` | program region checksum |
| КС ПЗУ | `[2816]0379` | (не найдена как 32-битное слово) | вероятно CRC16/часть другого блока |

КС калибровки `DD5630D0` совпадает с 4 байтами по `0x0807FFFC`, которые меняются между `IMMOON` и `IMMOOFF` калибровками.

### Проверка гипотезы «триггер из КС»

Простые комбинации байт триггера с КС (XOR, конкатенация, CRC32/MPEG-2 от КС) не дают совпадения. Триггер, вероятно, собирается из флеш-данных **плюс изменяющийся счётчик сессии** (EEPROM/пробег/время), поэтому он меняется при каждом включении зажигания.

### Изменения в rusEFI

В `firmware/config/boards/m74_9/m74_9_can.cpp`:
- IMMO-автомат активируется только при `engineConfiguration->m74_9ImmoEnabled == true && !engineConfiguration->m74_9ImmoOff`.
- Кадры `0x0714` игнорируются, если IMMO выключен.
- `m74_9_isImmobilizerBlocking()` теперь возвращает:
  ```cpp
  return engineConfiguration->m74_9ImmoEnabled
         && !m74_9BcmListener.isImmoAuthenticated();
  ```

Это повторяет поведение оригинальной прошивки: при выключенном IMMO ЭБУ не инициирует обмен и BCM не требует аутентификации для запуска.

## Дальнейшие шаги

### Приоритет 1 — Собрать и проверить триггер-фикс

```bash
touch firmware/integration/rusefi_config.txt
cd firmware/config/boards/m74_9 && ./compile_m74_9.sh
```

Залить прошивку, подключить PCAN, включить зажигание. Через ~1 с
должен появиться кадр `0x0713` от ECU. BCM должен ответить двумя `0x0714`.
В логе ECU: `IMMO: challenge received but response algorithm not implemented`.
ECU повторяет триггер каждые 500 мс.

**Ожидаемый результат**: BCM больше не показывает CF-ошибку, движок заводится
(IMMO не блокирует топливо/зажигание, пока алгоритм = заглушка).

### Приоритет 2 — Unicorn-эмуляция с реальным вызовом

1. Снять новый PCAN-дамп — захватить 16-байтный вызов BCM для rusEFI.
2. Запустить `emulate_immo.py` с этими байтами в SRAM.
3. Попробовать разные варианты раскладки буфера (см. гипотезу выше).
4. Если SRAM настроен правильно — Unicorn выдаст правильный ответ.

Рецепт Unicorn-эмуляции:
```python
# SRAM настройка для FUN_08201E2C:
mu.mem_write(0x20000C14, bytes([0x14, 0x01, 0xFF, 0x00]))  # header
mu.mem_write(0x20000C18, challenge_16_bytes)                # данные
mu.mem_write(0x200002C8, bytes([1]))   # инициализировано
mu.mem_write(0x200003FE, bytes([1]))   # флаг готовности
# Регистры вызова:
mu.reg_write(R0, 1)         # key_type
mu.reg_write(R1, 0xFF00)    # session_word
mu.reg_write(R2, 0x20000C18) # data_ptr+4
mu.reg_write(R3, 12)        # count-4 (для 16-байтного вызова)
# Вызов:
mu.emu_start(0x08201E2C | 1, sentinel, ...)
# Захватить записи в 0x20000C18-0x20000C27
```

- Прочитать все регистры и SRAM

### Что найдено

**Ключевые константы в flash:**

| Адрес | Значение | Роль |
|-------|----------|------|
| `0x08200000` | `12 C2 A0 43 DD 7B 3C 50 C9 26 59 01 48 7A 33 2E` | 16-байтный блок; первые 4 байта = тип B маркер |
| `0x08204B74` | `0x2548A4D2` | Тип A маркер (в literal pool) |
| `0x08204B78` | `0x43A0C212` | Тип B маркер (= первые 4 байта 0x08200000 LE) |
| `0x08204BF0` | `0x4DF9123B` | Константа B (пишется в SRAM[0x20001ADC+4]) |
| `0x08204BEC` | `0x20001ADC` | SRAM-адрес куда пишется константа A |

**FUN_08204BAC** записывает при инициализации:
- `SRAM[0x20001ADC] = 0x2548A4D2` (ключевая константа A)
- `SRAM[?] = 0x4DF9123B` (ключевая константа B)

**FUN_08204B54** (type check) сравнивает SRAM-значение с константами
и возвращает: 0=тип A, 1=тип B, 2=неизвестно.

**State machine callbacks @ 0x08209A60:**
```
[0] 0x08205F58 - init (сброс state vars 0x20001B74, 0x20001B16)
[1] 0x08205F88 - ?
[2] 0x08205F9C - dispatch по state var
[3] 0x0820600C - flash attestation check (вызывает FUN_082056D4)
[4] 0x08206108 - flash region computation
[5] 0x082061D4 - read SRAM accumulator
[6] 0x082061E0 - XOR accumulator update
[7] 0x082062E8 - wrap-up
```

**FUN_082056D4** (flash 0xFF checker):
```c
int check_all_ff(uint8_t* addr, uint32_t size) {
    for (int i = 0; i < size; i++)
        if (addr[i] != 0xFF) return 0;
    return 1;  // all bytes are 0xFF
}
```

**Attestation карта флеша (1=все FF, 0=есть данные):**
```
Sector  0-15: 0000010000001110  (секторы 5,12,13,14 - намеренно стёрты)
Sector 16-31: 1111111111111111  (SLib = все FF)
Sector 32-47: 0101001011111111
Sector 48-61: 11111111111111
```

### Что попробовано (не дало совпадений)

Протестировано против 5 quick-пар (8→8) и 5 full-пар (trigger+F1+F2→response):

- **AES-128/192/256 ECB/CBC/CTR/GCM** - все варианты ключей, все входные комбинации
- **DES, 3DES ECB/CBC** - все 8/24-байтные ключи из флеша
- **HMAC-MD5/SHA1/SHA256** - все ключи, все входные комбинации
- **AES-CMAC** - все 16-байтные ключи
- **XTEA** - все порядки 4 констант
- **CRC32 XOR** выбранных секторов по bit-mask из challenge
- **Attestation bitmap** → AES/HMAC
- **Перебор по всему флешу** (каждые 4 байта как потенциальный AES ключ, первые 200KB)

**Вывод**: алгоритм либо нестандартный, либо входные данные проходят
нетривиальную предобработку перед криптографической операцией.

### Почему не совпадает

1. **Challenge format не декодирован** - байты Frame1+Frame2 не используются
   напрямую как криптовход. CAN ISR трансформирует их перед сохранением в SRAM.
2. **Многошаговый алгоритм**: challenge → flash_start/flash_size → чтение flash →
   аккумуляция результата → финальная крипто-операция с ключом.
3. **Промежуточные данные** (accumulator в SRAM[0x20001B74]) - видны только
   при живой трассировке через OpenOCD.

## Новые находки от декомпиляции (2026-08-14)

### Таймеровый фреймворк и `FUN_08201716`

`FUN_08201716` — это **не** криптография, а обработчик одного из состояний IMMO-автомата:

- `0x20000220` — массив из 10 программных таймеров, каждый по 12 байт.
- `FUN_082010d4(index, timeout)` — запуск таймера (устанавливает `counter=0`, `timeout=timeout`, бит активности).
- `FUN_08201104(index)` — сброс/остановка таймера.
- `FUN_08201716` сбрасывает таймер `0x20000299`, запускает таймер `0x2000029A` на **1000 мс** и переводит state в `5`.

### Главный IMMO state machine — `FUN_082013d0`

`FUN_082013d0(param_1, param_2)` разбирает входящие 8-байтные кадры `0x0714`:
- `param_1`: 0 или 1 (подтип/команда)
- `param_2`: указатель на 8 байт данных
- старший ниббл первого байта — команда, младший — длина

Основные состояния:

| State | Действие |
|-------|----------|
| 0 | Ожидание. При кадре с `param_1==1` и ст.нibble==1 выделяет буфер `0x20000414`, копирует 6 байт, сохраняет session word, отправляет `0x30 00 00 00 00 00 00 00`. |
| 1 | Подготовлен к приёму. |
| 2 | Пришёл второй кадр `0x0714` (ст.нibble==2). Докидывает данные в буфер `0x20000414`. По заполнению вызывает callback B (`FUN_082020f0`) с `param_1=1`, который сохраняет session word в `0x20000402` и ставит флаг `0x200003EE = 1`. |
| 5 | Quick-check. При мл.нibble==0 сохраняет `param_2[1]` в `state[0x1c]`, переходит в state 6 и вызывает `FUN_08201260`. |
| 6 | `FUN_08201716`: сброс/запуск 1000 мс таймера, state=5. |

### Зарегистрированные коллбэки A/B/C

Инициализация в `0x08203620`:

```c
bl FUN_08201350;                 // alloc timer slots
ldr r2, =0x08202199;             // callback C
ldr r1, =0x082020F1;             // callback B
ldr r0, =0x082020C1;             // callback A
bl FUN_082013B4;                 // register callbacks
```

- **Callback A** (`0x082020c0`): буфер-аллокатор — возвращает `0x200003F4` или `0x20000414`.
- **Callback B** (`0x082020f0`): управление сессией/флагами (`0x200003ED`, `0x200003EE`, `0x20000402`).
- **Callback C** (`0x08202198`): завершение/диспатч — проверяет флаги `0x200003EC`, `0x200003F1`, `0x200003EF` и вызывает `FUN_0820511c` / `FUN_08204c14` / `FUN_08204c22`.

### Отправка 8-байтных `0x0713`

- `FUN_08201208(len)` — byte0 = session_low_nibble, bytes 1..7 = данные.
- `FUN_082012e8()` — byte0 = `(session >> 8) | 0x10`, byte1 = session, bytes 2..7 = данные.
- `FUN_08201260(len)` — byte0 = retry_count | 0x20, bytes 1..7 = данные + 0xCC.
- Все три вызывают `FUN_08204ab8(0, data, 8)` — общий CAN-диспетчер, который копирует данные в CAN TX mailbox.

### `FUN_08202e20` — вычисление и отправка ответа

```c
void FUN_08202e20(param_1) {
    session = *0x20000402;
    if ((session - 1) < 7) {
        first_byte = *0x20000414;           // первый байт challenge
        local_12 = 0;
        // Вызов функции из таблицы 0x20001018, слот +0x00
        fn = *(code**)(0x20001018 + *0x200003FC * 0x54);
        result = fn(first_byte, 0x20000415, session - 1, 0x20000C19, &local_12);
        if (result == 0) {
            *0x20000C18 = first_byte | 0x40;  // RESPONSE-формат
            FUN_08201660(0x20000C18, local_12 + 1);
        } else {
            FUN_08202254(param_1, result);
        }
    }
}
```

Это подтверждает, что bit 0x40 в первом байте ответа формируется здесь. Функция в слоте `+0x00` таблицы `0x20001018` — основной кандидат на крипто-алгоритм.

### `FUN_08202cbc` — обработка первого кадра challenge

- Проверяет `0x20000402 == 2`.
- Читает `0x20000415` (второй байт challenge).
- Допустимые типы challenge: `1, 2, 3, 0x60, 0x61, 0x62, 0x63`.
- Вызывает CAN-функции из таблицы `0x20001018`, слот `+0x04`.
- При `param_2 == 0` отправляет `50 bVar6 00 32 01 F4`.
- Переключает индекс `0x200003FC` на вычисленное `iVar7`.
- Запускает таймер `0x2000029B` на 5000 мс.

### `FUN_0820511c` — сброс процессора

```c
void FUN_0820511c(void) {
    SCB->AIRCR = 0x05FA0004;  // system reset request
}
```

### Таблица диспатча `0x0820868C`

Таблица по адресу `0x0820868C` содержит 64 указателя (256 байт). Известен только первый диапазон:

| Entry | Адрес | Функция |
|-------|-------|---------|
| 0x00–0x09 | `0x08202E21` | `FUN_08202e20` (вычисление и отправка IMMO-ответа) |
| 0x0A–0x3F | — | пока не разобраны |

Остальные записи, судя по смещениям, передают управление в `FUN_08202cbc`, UDS/диагностику и вложенные подтаблицы.

#### Рекомендуемая трассировка через OpenOCD

- Breakpoint в `fn[3]` (`0x0820600C`) или `fn[4]` (`0x08206108`).
- Читать R0 (`flash_start`), R1 (`flash_size`), SRAM[`0x20001B74`] (`accumulator`).
- После каждого шага state machine видеть промежуточный результат.

Для этого нужен BCM с кадрами из `orig_*.trc` (см. раздел PCAN выше).

### Расширенные декомпиляции IMMO-функций

#### `FUN_08201716` — переход в состояние 5 с таймером 1000 мс

```c
undefined4 FUN_08201716(void)
{
  FUN_08201104(*DAT_082017d0);          // сброс таймера 0x20000299
  FUN_082010d4(*puRam082017d4, 1000);   // запуск таймера 0x2000029A на 1000 мс
  *(byte *)(iRam082017c4 + 0x10) =
      *(byte *)(iRam082017c4 + 0x10) & 0xf0 | 5;  // state = 5
  return 0;
}
```

Это объясняет наблюдаемую задержку ~1 с между включением зажигания и первым кадром `0x0713`: ЭБУ сначала выполняет внутреннюю обработку challenge, затем запускает 1000 мс таймер и переходит к отправке.

```text
  r2 = 0x08202199   ; callback C (dispatch)
```

`FUN_082021e5` (timer callback):

```text
if (arg == 0) {
    idx = SRAM[0x200003FC];
    fn = table[0x20001018 + idx*0x54 + 0x04];
    if (fn && fn(0) == 0) {
        type = FUN_08204c30();
        SRAM[0x200003FE] = 0;
        SRAM[0x200003FC] = 0;
        stop timer 0x20000410;
        if (type == 2) FUN_08204c22();  // reset
    }
} else if (arg == 1) {
    SRAM[0x200003F2] = 0;
    stop timer 0x20000413;
}
```

### 3. Таблица зарегистрированных функций `0x20001018`

Регистраторы находятся в блоке `0x082036c0..0x08203788`:

| Адрес регистратора | Смещение в слоте | Назначение |
|--------------------|------------------|------------|
| `0x082036c4` | `+0x04` | общий guard/инициализация |
| `0x082036e0` | `+0x10` | full-challenge стадия 1 |
| `0x08203700` | `+0x14` | full-challenge стадия 2 |
| `0x08203718` | `+0x34` | основной крипто-алгоритм (вызывается из `FUN_08202e20`) |
| `0x08203734` | `+0x3c` | быстрый перезапуск/сброс |
| `0x08203750` | `+0x40/+0x44` | flash-attestation параметры |
| `0x08203770` | `+0x4c` | quick-check guard |

Регистрация для `idx = 1` происходит в `FUN_08202038`:

```text
0x08202038:
  table[1].+0x04 = 0x08202019
  table[1].+0x34 = 0x08201e2d
  table[1].+0x3c = 0x08201df1
  table[1].+0x40 = 0x08201d85, table[1].+0x44 = 0
  table[1].+0x4c = 0x082017d9
  table[1].+0x10 = 0x08201ae1
  table[1].+0x14 = 0x082017f9
```

`FUN_08201e2c` — основной обработчик full-вызова: проверяет
`SRAM[0x200003FE] == 1`, парсит `session_word` (`0xFF00` / `0xFF01`),
по пути `0xFF00` вызывает `FUN_0820630c` (flash-attestation), по пути
`0xFF01` переходит в SLib-ветку через `FUN_08204bac`.

`FUN_08201df0` сохраняет `r0/r1` в `0x200002D4/0x200002D8` и сбрасывает
`0x200002DC`.

`FUN_08201d84` запускает flash-attestation: вызывает `FUN_08206108` с
`flash_start = SRAM[0x200002D4]`, `flash_size = SRAM[0x200002D8]`.

### 4. Обработчик первого кадра challenge — `FUN_08202cbc`

- Проверяет `SRAM[0x20000402] == 2` и тип второго байта challenge
  (`1,2,3,0x60..0x63`).
- По типу выбирает новый `idx` (`0..6`) и вызывает `table[idx].+0x04`.
- Если guard возвращает `0`, устанавливает `SRAM[0x200003FC] = idx`,
  `SRAM[0x200003FE] = 0` (!), запускает таймер `0x20000410` на 5000 мс.
- Для `param_2 == 0` отправляет `50 bVar6 00 32 01 F4` через `FUN_08201660`.

**Важно**: `FUN_08202cbc` **сбрасывает** `0x200003FE` в `0` после приёма
первого challenge-кадра. Это означает, что флаг `0x200003FE` используется
только до начала обмена; после получения challenge дальнейшая работа
идёт по state-machine.

### 5. Геттер IMMO-флага `FUN_082037d8`

```text
FUN_082037d8:
  ldr r3, [pc, #0x200003FE]
  ldrb r0, [r3]
  bx lr
```

Многие IMMO-функции (`FUN_08201e2c`, `FUN_08201df0`, `FUN_08201d84`,
`FUN_082017d8` и др.) начинаются с `bl FUN_082037d8` и возвращают
ошибку `0x33`, если флаг не равен `1`.

**Пока не найден setter**, который устанавливает `0x200003FE = 1`.
Единственные найденные записи в `0x200003FE` — обнуление
(`0x08202212`, `0x08202d56`). Это подтверждает гипотезу, что флаг
выставляется на раннем этапе инициализации (shared library или SLib)
на основе байта калибровки `0x08074BF9`.

### 6. Calibration descriptor table и pointer table

- Pointer table по адресу `0x0803E590` содержит 4 указателя:
  `0x0804A900`, `0x08046D08`, `0x08049A08`, `0x080460F8`.
- `0x0804A900` — таблица дескрипторов калибровок.
- В таблице есть записи для `0x08074BF8` и `0x08074BF9` (item ~28/29),
  что совпадает с единственным отличием `IMMOOFF`/`IMMOON`.
- Прямых ссылок на `0x0804A900`, `0x0803E590` или адреса калибровки
  из кода `0x082xxxxx` не обнаружено; доступ идёт через pointer table
  и, вероятно, через shared library `0x080xxxxx`.

### 7. Статус поиска генератора триггера `0x0713`

- Триггер отправляется через `FUN_08201208` / `FUN_08201260` /
  `FUN_082012e8` -> общий CAN-диспетчер `FUN_08204ab8`.
- Первичный «таймер включения зажигания» — `0x20000410` с callback
  `0x082021e5`. Его точка запуска (возможно, по событию IGN ON или
  по истечению 1000 мс внутри `FUN_082017d8`/`FUN_082017f8`) пока
  не зафиксирована.
- **Генератор случайных/flash-зависимых 8 байт триггера ещё не найден**.
  Наиболее вероятные места:
  - SLib-вызовы `0x08069028` / `0x080697D0` (найдены ранее в
    `find_trigger_gen.py`);
  - функция в слоте `+0x14` (`0x082017f9`) или `+0x4c`
    (`0x082017d9`), которые вызываются в начале full/quick-обмена.
