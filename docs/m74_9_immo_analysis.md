# m74_9 immobilizer analysis notes

Этот документ содержит всё, что известно об иммобилайзере m74_9 / Itelma I865LB52 (Lada/Largus),
чтобы последующие сессии могли продолжать работу без повторной разведки.

---

## Текущий статус (обновлено 2026-08-14)

### Что исправлено

**Устранена мёртвая блокировка** в `firmware/config/boards/m74_9/m74_9_can.cpp`:

- Старый код запускал триггер при `byte4 == 0x44` (поворот ключа на старт).
- BCM **никогда** не выставляет `byte4=0x44`, пока IMMO-хэндшейк не завершён.
- rusEFI никогда не посылал триггер → BCM никогда не посылал вызов 0x0714 → стартер не крутил.

Исправление:
- Триггер теперь запускается при `byte4 != 0x00` (первый кадр BCM после включения зажигания).
- Задержка триггера: 100 мс → 1000 мс (оригинальный ЭБУ посылает ~1.5 с по трейсам).
- `m74_9_isImmobilizerBlocking()` теперь всегда возвращает `false` до реализации
  `computeImmoResponse()`, чтобы движок можно было запустить для тестирования протокола.
- `m74_9ImmoEnabled` убран из `m74_9_isImmobilizerBlocking()` (поле есть в
  `rusefi_config.txt`, но не было перегенерировано в хедере на хосте пользователя;
  исправлено убрав зависимость — функция всегда возвращает `false`).

### Обнаружено (SWD/JTAG сессия 2026-08-14)

- **Триггер 0x0713 — случайные 8 байт** каждый запуск (вероятно AT32F435 TRNG).
  BCM вычисляет Frame1+Frame2 из этого триггера по неизвестному алгоритму.
  rusEFI шлёт фиксированный счётчик — BCM отвечает другим форматом.

- **Окно приёма 0x0714 — 1.2..10.3 мс** после 0x0713 (avg 7 мс по 5 парам).
  Ручная отправка через PCAN-View (~100 мс) всегда опаздывает.

- **Формат Frame1**: байт[0] ДОЛЖЕН иметь бит 0x40 (RESPONSE-формат).
  Во всех 5 парах оригинального ЭБУ Frame1[0] ∈ {0x66, 0xCF, 0x4A}.
  Данные `26 17 14 F0...` (от BCM→rusEFI) не принимаются оригинальным ЭБУ.

- **ЭБУ не проверяет challenge против своего trigger** — FUN_08201E2C проверяет
  только key_type==1 и session_word==0xFF00/0xFF01. Любой корректно-форматный
  0x0714 (с правильным байт[0]) должен приниматься.

- **Корректные тестовые данные** (из orig_1.trc, пара 1):
  - Frame1: `66 0B E1 E2 A3 4B 81 40`
  - Frame2: `B4 56 33 A0 49 9A 01 EC`

### Что ещё не сделано

`computeImmoResponse()` и `computeImmoQuickResponse()` — заглушки, возвращающие `false`.
Алгоритм ответа не реализован. Движок запустится (IMMO не блокирует), но BCM будет
периодически посылать повторные вызовы 0x0714, на которые ECU не отвечает.

Breakpoint на `0x082078D4` (BLX R3 = вход в SLib) ещё не сработал:
нужны правильные данные (Frame1[0] с битом 0x40) + автоматическая отправка < 10 мс.
См. `immo_respond.py` и инструкцию ниже.

## Протокол CAN (подтверждён анализом трейсов PCAN-View)

### Идентификаторы сообщений

| ID     | Направление | Период | Описание |
|--------|-------------|--------|----------|
| 0x0350 | BCM → ECU   | 100 мс | Статус BCM; byte4 кодирует фазу IGN/пуск/реле/работа |
| 0x0303 | BCM → ECU   | 100 мс | Статус реле; bit1 byte5 = реле стартера активно |
| 0x0714 | BCM → ECU   | ~200 мс (пересылка) | IMMO-вызов от BCM |
| 0x0713 | ECU → BCM   | по событию | IMMO-триггер (инициирует) + ответ (после вызова) |
| 0x01F6 | ECU → BCM   | 10 мс  | Статус двигателя |
| 0x0189 | ECU → BCM   | 10 мс  | RPM primary (0x3200 в покое!) |
| 0x0186 | ECU → BCM   | 10 мс  | RPM aux |
| 0x018A | ECU → BCM   | 10 мс  | RPM aux2 |
| 0x0217 | ECU → BCM   | 10 мс  | Статус ECU |
| 0x02A9 | ECU → BCM   | 10 мс  | Heartbeat |
| 0x02C6 | ECU → BCM   | 20 мс  | Статика |
| 0x05E2 | ECU → BCM   | 1000 мс| Keepalive |
| Burst  | ECU → BCM   | 100 мс | 11 кадров идентификации (05DA, 036E, 03A5, …) |

### Полный цикл аутентификации

1. ECU включает зажигание → ждёт ~1.5 с
2. ECU посылает 0x0713 **триггер** (8 байт, случайные сессионные данные)
3. BCM отвечает двумя 0x0714 кадрами подряд (~0.2 мс между ними) = 16-байтный вызов
4. ECU вычисляет ответ (~15–20 мс) и посылает 0x0713 **ответ** (8 байт)
5. BCM проверяет ответ
6. BCM начинает периодически посылать 0x0714 quick-check (1 кадр, 8 байт) каждые ~200 мс
7. ECU отвечает на каждый quick-check в течение ~5 мс

### Статусная машина BCM (0x0350, byte4)

| byte4  | Значение |
|--------|----------|
| `0x00` | BCM выключен / зажигание выключено |
| `0x04` | Зажигание включено, IMMO не пройден (CF состояние) |
| `0x44` | Ключ повёрнут на старт (crank switch) — только после IMMO! |
| `0x84` | Реле стартера активно (BCM выдал GND на реле) |
| `0xC4` | Двигатель работает |

**Важно**: BCM никогда не выставит `0x44` или выше, пока IMMO-аутентификация не пройдена.
Стартером управляет полностью BCM — пин starter relay на ECU не используется.

**Поле CF** в `0x0350 byte0`: если ECU посылает `0x0000` в первых двух байтах `0x0189`
(RPM baseline), BCM входит в режим CF-ошибки и отказывается закрывать реле стартера даже
при правильном IMMO. Обязательно посылать `0x3200` как baseline когда двигатель стоит.

### Вызовы от BCM для rusEFI (новые данные 2026-08-13)

**Критическое наблюдение**: Frame1 = `26 17 14 F0 94 E7 29 7F` одинакова
для ВСЕХ 10 сессий rusEFI (только Frame2 случайна).

Это означает: Frame1 — фиксированный идентификатор BCM (не производная от триггера),
а Frame2 — случайный nonce.

Frame1 для rusEFI всегда: `26 17 14 F0 94 E7 29 7F`
```

  frame2=c0a376b3e9fdb85f  -> response НЕИЗВЕСТЕН
  frame2=e1f1651d533d54b8  -> response НЕИЗВЕСТЕН
  frame2=a2699d694b45d96e  -> response НЕИЗВЕСТЕН
  frame2=976ad10d9a3de065  -> response НЕИЗВЕСТЕН
  frame2=619adfc29b480a80  -> response НЕИЗВЕСТЕН
  frame2=f38352b522a50ddb  -> response НЕИЗВЕСТЕН
  frame2=8ddf022d20c69e89  -> response НЕИЗВЕСТЕН
  frame2=59ef563691af1d46  -> response НЕИЗВЕСТЕН
  frame2=ee8cc257e2644898  -> response НЕИЗВЕСТЕН
```

Чтобы получить ответы: поставить оригинальный ЭБУ, снять PCAN-дамп.
BCM пошлёт те же вызовы (Frame1=2617...), оригинальный ЭБУ даст ответы.

### Frame1 структурный анализ

Frame1 = `26 17 14 F0 94 E7 29 7F`
- Byte[0] = 0x26 = 38 (возможно, Service ID)
- Byte[1] = 0x17 = 23 (возможно, Sub-function ID)
- Byte[2] = **0x14** → n1=4, n2=1 — единственный байт с обоими nibble ≤ 4!
- Byte[3..6] = F0 94 E7 29 → r8 = 0xF094E729 (BCM's ключевой материал)
- Byte[7] = 0x7F → r5 = 0x7F (дополнительный параметр)

Паттерн `2617` найден в flash calibration по адресам:
- 0x0804E87A, 0x08063891, 0x08063A91
(вероятно, ожидаемый Frame1 хранится в калибровке ECU для проверки)

### Quick 8-байтный вызов → 8-байтный ответ (периодическая проверка)

```
challenge 0eabfe9d351af837 -> response b15156d14683cd15
challenge 4a90250e855128bf -> response 14a267bec8d8c3dc
challenge 63b95b1a3fbf41fe -> response 2fa71d4722835ea2
challenge 596e3885f2460f4a -> response 2cdf61de56551b86
challenge a00059b79f90a8ae -> response a225de4e470324b6
```

Что **проверено и исключено** при поиске алгоритма:
- XOR (все смещения), ADD, SUB mod 256 — нет константного ключа
- AES-128-ECB (все 16-байтные блоки flash в диапазоне 0x080400–0x090000) — не найдено
- SHA-1, SHA-256, MD5 — нет
- CRC32 — нет
- XTEA/TEA (32 раунда, LE и BE) — нет
- Простое чтение flash (ответы не найдены в бинарнике verbatim) — нет

Алгоритм **проприетарный**, использует ADD/XOR/shift с ключом из калибровочной области flash.

## Цепочка обработки CAN-приёма

```
CAN1_RX0_IRQ (0x08207432)
  → FUN_08207432  (выравнивание стека)
  → FUN_08206FB8(channel=0)  (универсальный CAN-диспетчер)
      читает CAN_RDT0R[15:8] = FMI (Filter Match Index)
      ищет обработчик в таблице 0x08209834
      → per-frame handler (для 0x0714 — хранит байты в SRAM 0x20000C14)
      → глобальный коллбэк *SRAM[0x20001BFC]
          → FUN_08204AB8 → таблица 0x082090E0 → обработчики по CAN ID
```

CAN1_RX использует **FMI** (индекс совпавшего фильтра), а не прямой CAN ID для диспатча.

## SRAM-таблица зарегистрированных функций

База: `0x20001018`, шаг: `0x54` на запись (индекс 0..6).
Каждая запись — структура с указателями на функции по разным смещениям.

**Зарегистрированные слоты (индекс 1, все адреса Thumb = нечётные)**:

| Смещение | Зарегистрированный адрес | Назначение |
|----------|--------------------------|-----------|
| `+0x04`  | `0x08202019` (fn @ 0x08202018) | Управление CAN-каналом |
| `+0x10`  | `0x08201AE1` (fn @ 0x08201AE0) | UDS DID обработчик (F188–F199) |
| `+0x14`  | `0x082017F9` (fn @ 0x082017F8) | Дополнительный обработчик |
| **`+0x34`** | **`0x08201E2D` (fn @ 0x08201E2C)** | **IMMO-обработчик вызова** |
| `+0x3C`  | `0x08201DF1` (fn @ 0x08201DF0) | Хранит flash_start, flash_size |
| `+0x40`  | `0x08201D85` (fn @ 0x08201D84) | Вызывает вычислительную функцию |
| `+0x44`  | `0` | Парный параметр к +0x40 |
| `+0x4C`  | `0x082017D9` (fn @ 0x082017D8) | Дополнительный обработчик |

Регистраторы (устанавливают слоты в таблице):
- `0x08203718` → записывает в `+0x34` (IMMO-обработчик)
- `0x08203734` → записывает в `+0x3C`
- `0x08203750` → записывает в `+0x40` и `+0x44`
- `0x08203770` → записывает в `+0x4C`
- `0x082036C4` → записывает в `+0x04`
- `0x082036E0` → записывает в `+0x10`
- `0x082036FC` → записывает в `+0x14`

Инициализация: `FUN_08202038` (PUSH @ 0x08202038) вызывает все регистраторы при старте.

## Цепочка вычисления IMMO-ответа

### Шаг 1 — Вычислитель 0x082027A4

Вызывается, когда нужно вычислить ответ на 16-байтный вызов BCM:

```
FUN_082027A4(r0=session_handle)
  r3 = SRAM[0x20000C14] count word  (> 3)
  r4 = SRAM[0x20000C15] & 0x7F      (key_type = 1)
  r1 = SRAM[0x20000C15]             (table_index)
  r2 = 0x20001018 + r1 * 0x54       (table entry ptr)
  r6 = [r2, #0x34]                  (fn ptr → FUN_08201E2C)
  blx r6  ← вызов IMMO-обработчика с:
    r0 = key_type (1)
    r1 = session_word (bytes [2:3] из 0x20000C14)
    r2 = 0x20000C18  (data_ptr + 4, начало данных вызова)
    r3 = count - 4
    sp+0 = 0x20000C1C  (буфер ответа)
    sp+4 = 0x3FC
    sp+8 = &output_len  (счётчик выходных байт)
```

### Шаг 2 — IMMO-обработчик FUN_08201E2C (@ +0x34)

```c
FUN_08201E2C(r0=key_type, r1=session_word, r2=data_ptr+4, r3=count-4):
    // Проверки:
    FUN_082037D8() → возвращает SRAM[0x200003FE] (должен быть 1)
    assert key_type == 1
    assert session_word == 0xFF00 или 0xFF01

    // Парсинг данных вызова (первый байт кодирует длины):
    byte0 = data[0]
    n1 = byte0 & 0xF   (кол-во байт для r8, должно быть ≤ 4)
    n2 = byte0 >> 4    (кол-во байт для r5, должно быть ≤ 4)
    r8 = big-endian аккумулятор из data[1..n1]       (flash_start?)
    r5 = big-endian аккумулятор из data[n1+1..n1+n2] (flash_size?)

    // Проверка SRAM[0x200002C8]:
    if == 0: вызвать FUN_08204B54 (первичная инициализация)
    if == 1: вызвать FUN_0820630C(r8, r5) (собственно вычисление)

    // FUN_08201E2C ВСЕГДА возвращает не-0 (асинхронный режим).
    // Вызывающий код при не-0 идёт в "error path" → FUN_08202254,
    // которая управляет асинхронным состоянием.
```

### Шаг 3 — FUN_0820630C (асинхронный движок)

```c
FUN_0820630C(r0=flash_start, r1=flash_size):
    FUN_0820566C(flash_start + flash_size - 1)  // проверка диапазона
    SRAM[0x20001B16] = 1  // state = busy
    FUN_082057F4()   // сброс FLASH_CR прерываний
    FUN_0820587C()   // очистка FLASH_SR флагов
    FUN_08205910()   // включение EOPIE прерываний
    FUN_08205950(flash_start, flash_size)   // настройка сессии
    SRAM[0x20001B60..] = {flash_start, flash_size, ...}
    FUN_08205D24()   // запуск операции (SER/MER биты в FLASH_CR)
    FUN_08205AB0(1)  // проверка готовности канала
```

### Шаг 4 — Flash ISR FUN_082063FC

```
FLASH_IRQHandler (0x082063FC):
    читает FLASH_SR (0x40023C00 + 0x0C), проверяет EOP (бит 5)
    если EOP set → очищает флаг, вызывает *SRAM[0x20001B88]
    SRAM[0x20001B88] содержит коллбэк, зарегистрированный при настройке
```

### Шаг 5 — FUN_08206108 (вычисление на flash-данных)

```c
FUN_08206108(r0=flash_start, r1=challenge_data_ptr, r2=length):
    FUN_08205A3C(flash_start, challenge_data_ptr, length):
        SRAM[0x20001B60]   = flash_start
        SRAM[0x20001B60+4] = challenge_data_ptr
        SRAM[0x20001B60+8] = length
        lookup в таблице 0x082093D8 (flash region table)
        SRAM[0x20000100]   = hw_variant byte из таблицы
        FUN_082059DC()  // настройка flash hardware
        FUN_08205A2C()  // дополнительная настройка
    FUN_08205AB0(2)
    FUN_08208408(2)   // диспатч → асинхронный коллбэк
```

### Шаг 6 — FUN_082056D4 (базовая проверка flash)

```c
FUN_082056D4(r0=flash_addr, r1=flash_size) -> 0 или 1:
    for i in 0..flash_size-1:
        if flash[flash_addr + i] != 0xFF:
            return 0   // регион запрограммирован (не стёрт)
    return 1           // регион стёрт (все байты 0xFF)
```

Эта функция вызывается для каждого байта/чанка результата в состоянии state=3/5/6 в
`FUN_082061F0`. Результат (0 или 1) накапливается в буфере ответа. Это не прямое чтение
flash — это **flash attestation** (проверка что firmware запрограммирована).

### Шаг 7 — Коллбэк FUN_08201A48 (отправка ответа)

```c
FUN_08201A48(r0=status, r1=data_or_zero):
    if r0 == 1 and r1 == 0:
        // "ключ верифицирован" — посылает [1, 0xFF, 0, 0] с cmd=0x31
        FUN_0820378C(r0=0, r1=0x31, r2=stack_buf, r3=4, flag=1)
        // первый байт CAN = 0x31 | 0x40 = 0x71

    if r0 == 2 and r1 == 0:
        // "ответ вычислен" — посылает данные из SRAM[0x200002D0]
        ldr r2, SRAM[0x200002D0]   // указатель на данные ответа
        FUN_0820378C(r0=0, r1=0x36, r2=r2, r3=1, flag=1)
        // первый байт CAN = 0x36 | 0x40 = 0x76
        // SRAM[0x200002D2] = длина данных (16-битная)
        // SRAM[0x200002D4] = flash-курсор (сдвигается на length каждую итерацию)
        // SRAM[0x200002DC] = счётчик (сравнивается с flash_size для цикла)
```

**Примечание**: наблюдаемые ответы CAN начинаются с байт 0x9C, 0xBF и т.д.
Первый байт CAN **не** соответствует `cmd|0x40` через `FUN_0820378C`.
Возможно, окончательный ответ формируется иным путём или через другую точку отправки.

## Flash-таблица регионов (0x082093D8)

62 записи × 16 байт каждая:

```
+0x00  u32   range_start  (начало flash-региона)
+0x04  u32   range_end    (конец flash-региона)
+0x08  u32   min_session_mode
+0x0C  u16   flags
+0x0D  u8    hw_variant   → записывается в SRAM[0x20000100]
+0x0E  u16   padding
```

Поиск идёт по: найти запись, где `range_start ≤ flash_start ≤ range_end`.

## UDS-диспетчер (FUN_08201AE0 — НЕ связан с CAN IMMO напрямую)

Обрабатывает UDS DIDs 0xF188–0xF199 (плюс 0xFD09 для специального случая):

```
FUN_08201AE0(r0=DID, r1=..., r2=..., r3=...)
  sub.w r4, r4, #0xF100
  subs r4, #0x88        → r4 = DID - 0xF188 (0..17)
  tbh [pc, r4, lsl #1]  → таблица переходов по DID
```

TBH-таблица на 0x08201B6C (PC=0x08201B6C):

| Case | DID   | Target         | Действие |
|------|-------|----------------|---------|
| 0    | 0xF188 | 0x08201CE6    | ReadDataByIdentifier — читает sp+0x22 (sparePartNumber) |
| 1    | 0xF189 | 0x08201CFC    | ReadDataByIdentifier — читает sp+0x23 |
| 2–13 | error | 0x08201D5E    | error 0x31 |
| 14   | 0xF196 | 0x08201D02    | ReadDataByIdentifier — sp+0x21 |
| 15   | 0xF197 | 0x08201D10    | ReadDataByIdentifier — 8 bytes |
| 18   | 0xF19A | 0x08201D14    | ReadDataByIdentifier — sp+0x20 |
| 19   | 0xF19B | 0x08201D22    | ReadDataByIdentifier — 8 bytes |

FUN_08203AEC разбирает UDS-запрос перед TBH-диспатчем.

## Реализация в rusEFI

### A. Keepalive-кадры ECU (сигнал "ECU живой" для BCM)

Все кадры реализованы в `m74_9_can.cpp`:

```cpp
// 10 мс:
send0x01F6(isRunning, isCranking)   // статус двигателя
send0x0189(rpmEncoded, isRunning)   // RPM; ОБЯЗАТЕЛЬНО 0x3200 в покое!
send0x0186(rpmEncoded, isActive)
send0x018A(rpmEncoded, isRunning)
send0x0217(isEngineActive)
send0x02A9()  // heartbeat

// 20 мс:
send0x02C6()

// 100 мс:
sendBurst(isRunning)  // 11 кадров

// 1000 мс:
send0x05E2()
```

### B. IMMO-автомат (M74_9BcmCanListener)

```
Idle
  ↓ (byte4 != 0x00 в первом 0x0350, ждём 1000 мс)
WaitingToTrigger
  ↓ (посылаем 0x0713 trigger)
TriggerSent
  ↓ (принимаем первый 0x0714)
Challenge1Rx
  ↓ (принимаем второй 0x0714, через ≤10 мс)
ChallengeComplete
  ↓ (ждём 15 мс, вызываем computeImmoResponse())
ResponseSent   ← ФИНАЛЬНОЕ СОСТОЯНИЕ (пока не достигается — stub)

  При ResponseSent: одиночный 0x0714 → computeImmoQuickResponse()
  При TriggerSent timeout 500 мс: повтор триггера
```

### C. Конфигурационный бит

`bit m74_9ImmoEnabled` определён в `firmware/integration/rusefi_config.txt` (строка 2565).
После повторной генерации (`touch firmware/integration/rusefi_config.txt`) появляется
в `engine_configuration_generated_structures_m74_9.h`.

Пока алгоритм не реализован, `m74_9_isImmobilizerBlocking()` возвращает `false`

## Формат буфера вызова в SRAM (гипотеза)

При приёме 0x0714 BCM посылает данные, которые CAN-обработчик складывает
в SRAM начиная с 0x20000C14:

```
[0x20000C14] byte  count     = полный размер буфера (ожидается > 3)
[0x20000C15] byte  key_type  = 0x01 (стандартный ключ)
[0x20000C16] byte  session_hi= 0xFF
[0x20000C17] byte  session_lo= 0x00 или 0x01  → session_word = 0xFF00/0xFF01
[0x20000C18] 8 байт frame1_data  (байты 0–7 первого 0x0714 кадра)
[0x20000C20] 8 байт frame2_data  (байты 0–7 второго 0x0714 кадра)
```

Первый байт данных `[0x20000C18]` кодирует: `low_nibble=n1` (≤4), `high_nibble=n2` (≤4).
Все наши наблюдаемые вызовы имеют первый байт с обоими nibble > 4 → либо байты
хранятся иначе, либо SRAM заполняется CAN-обработчиком с предобработкой.

## Дальнейшие шаги

### Приоритет 1 — Собрать и проверить триггер-фикс

```bash
touch firmware/integration/rusefi_config.txt
cd firmware/config/boards/m74_9 && ./compile_m74_9.sh
```

Залить прошивку, подключить PCAN, включить зажигание. Через ~1 с
должен появиться кадр `0x0713` от ECU. BCM должен ответить двумя `0x0714`.
В логе ECU: `IMMO: challenge received but response algorithm not implemented`.
ECU повторяет триггер каждые 500 мс.

**Ожидаемый результат**: BCM больше не показывает CF-ошибку, движок заводится
(IMMO не блокирует топливо/зажигание, пока алгоритм = заглушка).

### Приоритет 2 — Unicorn-эмуляция с реальным вызовом

1. Снять новый PCAN-дамп — захватить 16-байтный вызов BCM для rusEFI.
2. Запустить `emulate_immo.py` с этими байтами в SRAM.
3. Попробовать разные варианты раскладки буфера (см. гипотезу выше).
4. Если SRAM настроен правильно — Unicorn выдаст правильный ответ.

Рецепт Unicorn-эмуляции:
```python
# SRAM настройка для FUN_08201E2C:
mu.mem_write(0x20000C14, bytes([0x14, 0x01, 0xFF, 0x00]))  # header
mu.mem_write(0x20000C18, challenge_16_bytes)                # данные
mu.mem_write(0x200002C8, bytes([1]))   # инициализировано
mu.mem_write(0x200003FE, bytes([1]))   # флаг готовности
# Регистры вызова:
mu.reg_write(R0, 1)         # key_type
mu.reg_write(R1, 0xFF00)    # session_word
mu.reg_write(R2, 0x20000C18) # data_ptr+4
mu.reg_write(R3, 12)        # count-4 (для 16-байтного вызова)
# Вызов:
mu.emu_start(0x08201E2C | 1, sentinel, ...)
# Захватить записи в 0x20000C18-0x20000C27
```

### Приоритет 3 — SWD-отладчик (самый быстрый путь)

Подключить JTAG/SWD к оригинальному ЭБУ с включённым зажиганием.
Поставить breakpoint на `0x082027FA` (`blx r6` в вычислителе).
Когда BCM пошлёт 0x0714:
- `r6` = адрес реальной крипто-функции
- Прочитать все регистры и SRAM
- Пройти пошагово, захватить 8-байтный ответ

### Приоритет 4 — Реализовать computeImmoResponse()

После нахождения алгоритма: реализовать в `m74_9_can.cpp`.
Восстановить `m74_9_isImmobilizerBlocking()` с проверкой `m74_9ImmoEnabled`.
Убедиться что BCM `byte4` достигает `0x84` (реле стартера), движок заводится.
