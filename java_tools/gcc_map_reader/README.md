# Firmware Stack Usage Report

`StackUsageReport` combines GCC's post-LTO callgraph data with stack metadata
linked into the firmware and bootloader ELF files. The report is informational:
it highlights changes for review but does not fail a build because a stack is
too small.

## Files

| Path | Reason                                                                                                  |
|---|---------------------------------------------------------------------------------------------------------|
| `src/main/resources/stack_usage/*.md` | Hand-maintained profile inputs: display names, reviewed measurements, proxy snapshots, and scenarios    |
| `firmware/build/firmware_stack_usage_<profile>.md` | Generated by `com.rusefi.tools.stack.StackUsageReport` during the stack-usage workflow                  |
| `docs/firmware_stack_usage.md` | Generated and committed by `.github/workflows/firmware-stack-usage.yaml` from the three profile reports |

Generated reports carry a header naming their generator. Do not edit generated
reports directly; update the firmware metadata, profile input, or report tool.

## Inputs

uses compiler-checked metadata macros from
`firmware/controllers/core/common_headers.h`:

- `RUSEFI_STACK_ROOT` for a `ThreadController` or `PeriodicController` member.
- `RUSEFI_STACK_ROOT_EXPLICIT` for a root with an explicit function and budget.
- `RUSEFI_STACK_PROCESS_ROOT` for the linker-sized main process stack.
- `RUSEFI_STACK_FOREIGN_ROOT` only for inaccessible upstream static functions.

The STM32 linker keeps this metadata in non-allocated ELF sections, so it adds
nothing to the flashed image. The Java tool reads:

- The full ELF symbol table for typed roots, including local symbols.
- Foreign-root string sections for inaccessible upstream functions.
- Linker map process and exception stack sizes.
- GCC `.ci` post-LTO callgraphs produced with `-fcallgraph-info=su`.
- The matching hand-maintained profile table under
  `src/main/resources/stack_usage/`.

Profile membership is exact. Adding or removing a linked root without updating
the corresponding profile table makes report generation fail with the missing
and extra entries.

## Run Locally

Build one profile with stack and callgraph data. For example, H743:

```bash
cd firmware
EXTRA_3_PARAMS="-fstack-usage -fcallgraph-info=su" \
  bash bin/compile.sh config/boards/nucleo_h743/meta-info.env \
  elf bootloader --output-sync=recurse
cd ..
```

Build, test, and run the Java report tool:

```bash
./gradlew :gcc_map_reader:test :gcc_map_reader:shadowJar
java -cp java_tools/gcc_map_reader/build/libs/gcc_map_reader-all.jar \
  com.rusefi.tools.stack.StackUsageReport \
  --profile stm32h743_nucleo \
  --firmware-dir firmware/build \
  --bootloader-dir firmware/bootloader/blbuild \
  --output firmware/build/firmware_stack_usage_stm32h743_nucleo.md
```

`arm-none-eabi-readelf` and `arm-none-eabi-c++filt` must be available on
`PATH`; command overrides are available through `--readelf` and `--cxxfilt`.

## Reading The Report

- **Nominal** is the allocated stack budget from C++ or the linker.
- **Reviewed** is a manually traced realistic scenario, not a root-wide maximum.
- **Proxy snapshot** is the post-LTO direct-call estimate when that scenario was
  reviewed.
- **Current proxy** is the estimate from the current build.
- `REVIEW PROXY +N` means the estimate grew and the scenario should be reviewed.
- `NOT REVIEWED` means no retained scenario exists for that root.

Indirect calls, unknown frames, recursion, interrupts, and context switching can
make the proxy incomplete. The report lists these limitations rather than
pretending the proxy is a proven maximum.
